Screen 08

Eval Detail — Failed (Critical UX)

This is the most important screen in the feature. When an eval fails, the Suggestion Island appears in the MiniRulebook's position. It has two sections: "Why it failed" (red header, explanation from the Grader agent) and "Suggested rulebook change" (blue header, the Grader's recommendation). The CTAs are "Re-evaluate" (re-run without changes) and "Accept" (view the proposed diff). This is the core loop: fail → suggestion → accept → diff → re-evaluate.

Why it failed
The agent accepted the 45-minute break without flagging it. Add an explicit escalation rule: when a break exceeds the allowed duration (30 minutes) and no supervisor approval is on record, the agent should send an alert to the supervisor and flag the shift for review. This gives the agent a clear action path instead of silently accepting the break.

Corner Cases

  • Grader can't determine a fix: hide "Accept" button, show only "Re-evaluate" with a note "The grader couldn't suggest a specific rulebook change for this failure"
  • Multiple issues in one eval: grader lists all failure reasons, suggestion addresses the primary one

  • User clicks "Re-evaluate" without accepting: eval re-runs with current (unchanged) rulebook
  • The problematic timeline row is highlighted in red to make the failure point obvious
Screen 09

Accept Flow — Diff View

When the user clicks "Accept" on the failed eval's suggestion, the Suggestion Island transitions to show a diff view. This uses the exact same diff UI as the existing MiniRulebook component: monospace font, green additions, red removals, line numbers, +N/-N stats. The buttons are "Discard" (return to suggestion) and "Apply Changes" (commit the rulebook modification). This is shown as an interactive state in Screen 08 above — click "Diff View" in the toggle to see it.
The diff view is embedded in Screen 08's Suggestion Island. Use the state toggle buttons to switch between Suggestion → Diff View → Accepted states. The diff reuses the exact same component pattern as MiniRulebook.tsx's diff phase.
Screen 10

After Accept — Re-evaluate

After applying the diff, the Suggestion Island collapses to a compact confirmation: a green checkmark, "Rulebook updated" message, and a prominent "Re-evaluate" button. The user's natural next action is to click Re-evaluate to verify the fix works. This is shown as the "Accepted" state in Screen 08's toggle above.
The full flow: Fail → read suggestion → "Accept" → review diff → "Apply Changes" → "Re-evaluate" → (eval runs again) → hopefully Pass. If it fails again, the cycle repeats with a new suggestion.

Corner Cases

  • User navigates away without re-evaluating: eval stays as "Fail" in the table, rulebook is already updated
  • User wants to manually edit the rulebook further before re-evaluating: they can go to the Workflows tab, make additional changes, then come back to re-evaluate
  • Re-evaluate fails again: new suggestion appears with updated reasoning (the grader knows the previous fix was applied)
Screen 11

Auto-Update Notification

When a rulebook changes, the system’s response depends on how the change originated. For manual edits (user changed rules on the Workflows page or via MiniRulebook), the Generator agent both re-runs existing evals and generates new evals to cover the changed rules. For eval-suggestion-accepted changes (a rulebook edit that came from accepting a failed eval’s suggestion), the system only re-runs existing evals — it does NOT generate new evals. This prevents a circular dependency: failed eval → suggestion → rulebook change → new evals → possible failure → another suggestion → infinite loop.

Corner Cases

  • Rapid successive edits: debounce the re-assessment, only trigger on the latest version
  • Agent removes an eval: show a brief toast notification “1 eval removed (no longer relevant)”
  • Agent modifies an eval’s expected outcome: show “Modified” badge instead of “New”, reset status to “Never Run”
  • No changes needed: banner briefly shows then dismisses with “No eval changes needed”
  • Eval suggestion accepted → re-run only: The system tags the rulebook change with source: “eval_suggestion”. The Generator checks this tag and skips new eval generation, only triggering re-runs of existing evals.
  • Manual edit after accepting suggestion: If the user makes additional manual edits before the re-run completes, the change source escalates to “manual” and full generation occurs.
  • Multiple suggestions accepted rapidly: Each acceptance triggers its own re-run-only cycle. Debouncing still applies — only the final state is evaluated.
Architecture

The Three Agents

The evals system relies on three distinct agents, each with a focused responsibility. All use Claude (Haiku to start, for cost management).
Generator

Reads the rulebook and produces eval scenarios with expected outcomes. Triggered on rulebook create/update. Adds, modifies, or removes evals as rules change.

Conductor

Executes evals by simulating both the worker and facility. Creates synthetic shift data, sends realistic messages, and follows the eval script. The agent being tested responds as it normally would.

Grader

Reviews the eval results against the expected outcome. Determines pass/fail. On failure, analyzes root cause and suggests specific rulebook changes with a concrete diff.
